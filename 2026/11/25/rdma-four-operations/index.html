通信原语背后的 RDMA ——理解四种 RDMA 操作

跟踪一条 4 KiB 消息的队列项、PCIe 事务和网络包，对照 SEND、WRITE、READ 和 Atomic，再从 RecoNIC 和 NCCL 源码看接收地址与完成通知怎样传递。
LEEcDiangChengzhan Li 2026.11.25 发布

A 要给 B 发 4 KiB 数据。用 SEND，A 可以一直不知道这 4 KiB 最后落在 B 的哪个地址。换成 RDMA WRITE，A 在提交请求时就得把那个地址填好。同样是把数据从 A 搬到 B，两张网卡分别要做什么？

上一篇讲一块张量为什么要从 A 传到 B。这次沿着它走一遍，从 A 的主存出发，经过两张网卡，再落到 B 的主存。文末回到 NCCL，看 B 怎样把可写地址告诉 A。

一、先找出缓冲区，再看网卡

A、B 各有一张 RNIC，两端已经建好 RC。图 1 中间是以太网，两张 RNIC 用 RoCEv2 收发数据，RDMA 传输包封装在 UDP/IP 中。[1]

应用先把一块缓冲区注册为 MR，再用 SGE 标出这次要用的部分。每条 SGE 里有起始地址、长度和 lkey。如果 B 打算让 A 远程写入，就给这块 MR 开远程写权限，并把地址和 rkey 告诉 A。随后 B 的 RNIC 就能检查这次写入是否在允许的范围内。[1][2]

图 1｜两台主机、一条网络和两段 PCIe。发一次普通的 4 KiB 消息，A 的 RNIC 从本地内存读出载荷，B 的 RNIC 把载荷写进自己的主机内存。图中选用主存队列、RNIC 主动取发送 WQE、载荷不内联的路径。

图 1 里，A 的程序提交一条 SEND WR。verbs provider 把它编码成 WQE，放进 SQ。CPU 随后通过 MMIO 写门铃，通知 A 的 RNIC 来取。RNIC 先用 DMA 从主存读出 WQE，再按里面的地址和长度取走要发的数据。[1][13]

B 的 RNIC 收到 SEND，先按包里的目的 QPN 找到 QP，再从 RQ 取出 B 预投的 WQE。A 只需指出从哪里读，往哪里写由 B 决定。写入完成后，B 的程序轮询 CQ，就能拿到这次接收的 WC。图中的发送 WR 设置了 IBV_SEND_SIGNALED，所以 A 也能从自己的 CQ 得知发送成功。[1][4]

一条 SEND 在主机里占几块内存

设 A 注册了一块 12 KiB 的内存，基址为 P。第一段从 P 起取 1024 B，第二段从 P + 8192 起取 3072 B，中间的空隙不用发送。A 用一条 SEND 引用两段内存，先列 1 KiB 的 SGE，再列 3 KiB 的 SGE。B 可以用一个连续的 4096 B 缓冲区接收，接到的字节顺序就是第一段接第二段。[1][3]

图 2｜A 端的 SQ 和载荷。上图按比例画出了两段源数据，中间空出的 7 KiB 不会上网。下图的读请求向左走，返回的数据向右走。最下面一行对应整条 SEND 的本地完成。

提交函数返回时，A 的 RNIC 可能还没读完第二段。如果程序这时覆写缓冲区，发出去的数据就可能变了。A 提交 WR 时可以给它一个 wr_id，等轮询 CQ 拿到这条 WR 的成功 WC，再复用两段内存。wr_id 留在本端。以 mlx5 为例，provider 会先把它存下来，轮询时再根据硬件返回的信息找回它。[3][4][13]

二、同一对网卡，四种操作

先播放 SEND，再切到 WRITE，看看 B 端的目的地址是从哪里来的。选“带立即数”时，数据仍写到同一个槽，可以留意 B 的 RQ 和 CQ 各有什么变化。动画把 A 要发的 4 KiB 统称为 TX，图 2 展示了它来自两个地址时的读法。

SEND 由 B 决定消息落在哪儿

B 先留出一块够大的缓冲区 RX7，调用 ibv_post_recv 向 RQ 提交一条指向它的 WR。A 提交 SEND 时只填本地 SGE，不必知道 RX7 在哪里。A 的 RNIC 从主存读出 4 KiB 发往 B。B 的 RNIC 从 RQ 取下一条 WQE，才知道要把这 4 KiB 写在哪里。[1][3]

B 轮询 CQ 后，从 WC 的 wr_id 找到对应的 RX7，也能读出实际收到的长度。如果包到了，RQ 里却没有可用的 WQE，B 的 RNIC 可以回复 RNR，A 的 RNIC 按配置重试。即使 A 已经收到 ACK，B 的程序也可能还没来得及轮询 CQ。[1][4]

左右滑动查看完整图表；键盘聚焦后可用方向键。

图 4｜同一条 SEND 可以装进一个包，也可以拆成四个。横向长度代表应用载荷字节数。两行均假设传输成功、无重传，B 预投了足够大的接收缓冲区。图中不计报头和 ACK。

把这条 SEND 的 PMTU 设为 1024 B，RNIC 在网络上依次发 First、Middle、Middle、Last 四个包。四个包合起来才是一条消息，B 只消耗一条接收 WQE，轮询 CQ 也只拿到一条 WC。改回 4096 B，网络上一个 Only 包就能发完，应用看到的完成数相同。[1][9]

同一笔 4 KiB，换到 PCIe 上会看到多少个事务？

只数载荷的搬运。假设两段源缓冲区和连续的目的缓冲区都从 4 KiB 页边界开始，PCIe 的 MRRS 为 512 B，两端相关路径的 MPS 都为 256 B。下表按每次都取到上限计算。[15]

观察位置 在链路上数什么 4 KiB 这一例
A 端 PCIe，RNIC 向主机发请求 MRd，每次请求 512 B 8 个
A 端 PCIe，主机向 RNIC 返回数据 CplD，每个至多带 256 B 16 个
两台机器之间的网络 PMTU 为 1024 B 的 SEND 数据包 4 个

两端 PCIe 计数中的 8、16、16 是上述条件下的最少数量。真实设备可以拆得更细，取 WQE、写 CQE 也另有流量。比如 A 的 RNIC 向主机读 512 B，至少要等两个 CplD 才收齐这一笔读请求的数据。B 的应用轮询时，只会得到一条对应整条 4 KiB 消息的 WC。

WRITE 把数据放进约好的位置

这次 B 在 MR 里留出 slot3，开好远程写权限，把槽的地址和 rkey 告诉 A。A 提交 RDMA WRITE 时，同时填写本地 4 KiB 的来源和 B 的目的地址。A 的 RNIC 照旧读本地内存，B 的 RNIC 检查请求后，直接把数据写进 slot3。和刚才的 SEND 相比，两端 PCIe 上大块数据的方向完全一样，换掉的是 B 查找写入位置的方法。[1][2][3]

普通 WRITE 不消耗 B 的接收 WQE，B 轮询 CQ 也收不到这笔写入的 WC。如果 B 还想知道哪一个槽可以读，可以约定用 WRITE_WITH_IMM。A 写入的目的地址仍是 slot3，同时附上一个 32 位立即数，比如槽号 3。B 为通知预投一条接收 WR，把它的 wr_id 设为 7。[1][3][4]

左右滑动查看完整图表；键盘聚焦后可用方向键。

图 5｜只看 B。实线跟踪 4 KiB 载荷，虚线跟踪接收通知。每一行是一次独立实验。最下一行，软件轮询所得的 wr_id = 7 由 B 填写，立即数 3 由 A 填写。

B 轮询得到的 WC 有两个值得看的字段。wr_id = 7 对应 B 预投的那条接收 WR，imm_data 经双方约定的编码解读为 3，告诉 B 去哪个槽读数据。两项都出现在一次轮询结果里，却来自两台机器。SEND 和 WRITE_WITH_IMM 都需要 RQ 里有可用的 WQE，否则 B 的 RNIC 可以回复 RNR。普通 WRITE 可以直接写入，但仍得等上层协议允许，A 才能覆盖 B 正在读的槽。[1][4]

还有一个细节在抓包时能看见。如果 WRITE 跨越多个传输包，远端起始地址、rkey 和总长度在 First 包的 RETH 里。Middle 和普通 Last 不再重发这三个字段。若是带立即数的多包 WRITE，立即数跟在 Last 包里。单包操作则在 Only 包里一次给齐所需字段。[16]

READ 的请求和数据往相反方向走

如果数据原本就在 B 的 slot3，而 A 想把它取回来，B 可以给这段内存开远程读权限，把地址和 rkey 交给 A。A 在 SQ 提交 READ，填的是 B 的源地址和 A 的目的缓冲区。离开 A 的先是一条读请求，写明从哪里读、读多少，4 KiB 载荷此时还在 B。[1][2][3]

看一笔 PMTU 为 1024 B、无重传的 4 KiB READ。A 只发一条读请求，B 的 RNIC 通过 B 端 PCIe 读出主存里的 4 KiB，把数据分进四个响应包。A 的 RNIC 收到它们后，按自己原先提交的 READ 请求，把数据写入 A 的目的缓冲区。B 只需要知道读自己哪块内存，A 的目的地址和本地 lkey 可以一直留在 A。A 拿到成功的 WC 后就可以读结果。B 无需为这次 READ 提交接收 WR，但要保证源内存在读取期间有效。[1][3][16]

Atomic 拿回计数器修改前的值

把 4 KiB 的槽换成一个 8 字节对齐的 64 位计数器，初值为 41。B 为它所在的 MR 开启远程原子权限，并把地址和 rkey 交给请求方。两台请求方都想领一个编号。如果各自先 READ，再把旧值加一 WRITE 回去，它们可能同时读到 41，最后都写回 42。明明领了两次号，计数器只走了一步。

支持远端原子的 RNIC 可以执行 FAA。A 给出远端地址、rkey 和加数 1，并留出本地的 8 字节结果缓冲区。B 对这个字做一次不可分割的读改写，计数器变为 42，返回 A 的是旧值 41。若两个请求都通过同一响应 RNIC 对这个字做 FAA，并且中间没有其他写入，它们会分别领到 41 和 42，最终计数为 43。谁先领到哪个号取决于操作的执行顺序。[3][10]

图 6｜A 和 C 通过 B 的同一张 RNIC 更新一个计数器。左边是先 READ 再 WRITE 的一种交错次序，右边让两个请求都执行 FAA。两次返回的旧值可以直接用作不同的编号。

另一种经典操作是 CAS。A 可以要求“若还是 41，就改成 99”。在演示的命中分支里，B 从 41 变为 99，A 收到 41。再切到未命中分支，这次 A 要求“若为 40，就换成 99”，B 的初值仍为 41，于是它保持 41，A 收到的也是 41。A 把返回的旧值与本次提交的期望值一比，就知道是否发生了替换。两种情况下，A 都能拿到成功的 WC。线上返回的是带旧值的 Atomic ACK，A 的 RNIC 把旧值写进结果缓冲区，A 从 WC 看执行状态，从结果缓冲区读旧值。[16]

经典 RC 原子操作针对一个 64 位字。能否与 B 的 CPU 或另一张网卡并发地对同一字做原子访问，取决于设备报告的原子能力范围。远端 RNIC 怎样实现这次读改写，verbs 也没有规定必须用某一种 PCIe 事务。[3][10]

三、一条 WRITE 在 RecoNIC 里怎么走

回到 WRITE 的例子。B 的 RNIC 收到了包，准备往主机内存里的 slot3 写 4 KiB。这次把图 1 中 B 的方框展开，换成 Alveo U250 上的 RecoNIC。它的板级设计和软件都可以查源码，负责处理 RoCEv2 的是 AMD 的许可 IP 核 ERNIC v3.1。[5][6]

左右滑动查看完整图表；键盘聚焦后可用方向键。

图 7｜RecoNIC 的收包分流和内存访问。沿以太网入口看，普通包与 RoCEv2 包进不同模块。沿 ERNIC 的内存接口看，目标可以是主机内存，也可以是板载 DDR。两边的 ERNIC 是同一个硬件模块。[5][6]

从网线进来，帧先到 CMAC。分类器把 RoCEv2 流量送给 ERNIC，普通网络流量另走常规收包路径。这个 WRITE 会进 ERNIC。找到目标缓冲区后，引擎从片上的 AXI 内存接口发出写入，经交叉开关和 QDMA 的 PCIe 桥到达主机内存。如果目的缓冲区在板载 DDR，写入就在板上结束。图里 QDMA 出现了两次。左边处理普通包的接收，右边给 ERNIC 提供通往主机内存的桥。[5][7]

网卡保存了什么，队列又放在哪里

选 RecoNIC 示例的 host_mem 配置，SQ、RQ 和 CQ 的存储在主机里。那 ERNIC 怎么知道该读哪一项？建 RC QP 时，软件把队列基地址和深度等参数交给硬件，同时配置远端 QPN、PSN、PMTU、重试参数及 PD。它们属于每条连接自己的状态。PG332 描述的 QP Manager 会在不同 SQ 之间仲裁，缓存已经取回的发送 WQE，再交给 WQE Processor 按 PMTU 组包、驱动 DMA。这样，主存里的 SQ 保存着 WQE，卡上也能暂存其中一项的副本。[6][7]

进来的 WRITE 还要查另一组信息。比方说 B 注册了 16 KiB，并分成四个连续的 4 KiB 槽，slot3 占用最后 4096 B。目的 QPN 让 ERNIC 找到连接。远端地址、rkey 和长度用来检查相应内存窗口与写权限。若把同一个写请求的起点再后移 64 B，尾部就越过窗口，ERNIC 不能把它作为合法的 4 KiB 写入执行。QPN 指出包属于哪条连接，ERNIC 还要核对 QP 与 MR 是否属于同一 PD，以及 MR 是否允许这次写入。[2][6]

RecoNIC 随库提供了 SEND/RECV、WRITE 和 READ 的双端示例。它自己的接收程序轮询 RQ 生产者索引，从预分配的槽取消息，用完再更新消费位置。在源码里，收到新消息的信号就是这个索引向前移动。前面动画中的应用通过 libibverbs 轮询 CQ，拿到接收 WC。这版 ERNIC 的手册也明确列出不支持 Atomic，图 6 的取号例子要用具备该能力的 RNIC。[6][8]

四、NCCL 的一次发送为什么会用 WRITE

跨机 AllGather 完成后，B 的结果缓冲区里应当有一段来自 A 的张量。只看这块张量怎样从 A 传到 B。至于每次传输怎样安排，NCCL 可以交给网络后端。即使上层用的是成对的 ncclSend 和 ncclRecv，RNIC 也可以用 RDMA WRITE 把这块数据送到位。下面跟的是内置 IB 后端的一个具体分支。[11][12]

B 先调用 ncclIbIrecv()，向 RQ 提交一条接收 WR。它有 wr_id，但 sg_list = NULL、num_sge = 0。这条 WR 留给写入通知使用，因此没有指定用来放张量的缓冲区。真正的落点由接下来的 ncclIbPostFifo() 公布。B 把地址、容量和 rkey 写进 A 那边的 FIFO 槽，A 读到它们以后，才知道往哪里写。[12][17]

左右滑动查看完整图表；键盘聚焦后可用方向键。

图 8｜NCCL v2.26.5-1 内置 IB 后端。固定一条消息、一个 QP，开启自适应路由并保留默认阈值 8192 B。两种大小共用 B 发布缓冲区的步骤，区别从 A 提交数据 WR 时开始。图中省略传输层 ACK。[12][17]

在这个分支里，ncclIbMultiSend() 判断消息大小是否严格大于 NCCL_IB_AR_THRESHOLD。把开头的 4 KiB 和一条 16 KiB 消息代进去，数一数 A 要提交几条 WR。

A 要发的数据 A 在这一条 QP 上提交的工作 B 从接收 WC 读回的大小
4 KiB 一条 WRITE_WITH_IMM，同时带 4096 B 张量数据和立即数 4096 B
16 KiB 一条普通 WRITE 搬 16384 B，再接一条零载荷 WRITE_WITH_IMM，串成链一次提交 16384 B

恰好 8 KiB 也走第一行的路径。第二行末尾的写没有第二份张量数据，却照样使 B 的 RNIC 写入 CQE。B 的代码从 wc->imm_data 取回原消息的长度，所以即便最后那条写的载荷长度为零，B 仍能读出 16384。图 5 里两端约定把这个字段用作槽号，NCCL 在这里用它传长度。表里数的是 A 传张量的 WR，前面 B 发布地址的那条控制 WRITE 两种情形都有。[12][17]

如果张量在 GPU 显存里，而且平台支持 GPUDirect RDMA，图 1 里指向主机 DRAM 的载荷箭头还可以改指向 GPU 显存。RNIC 可以直接走 PCIe 点对点访问这块内存。依赖这批数据的 GPU 内核何时可以启动，还要遵守 CUDA 和通信库的同步要求。[14]

回到开头的 4 KiB。用 SEND，B 把可写地址留在自己的 RQ 里。图 8 的方案则先把可写地址送到 A，所以 A 用一次带立即数的写就能把张量送到位。B 的网络后端收到了这一块的通知，接下来可以推进这笔传输。整个 AllGather 还要等其余分块满足依赖，而原来的槽什么时候能再次使用，取决于消费它的那一步是否已经结束。
