同样的矩阵乘法，为什么能差几个数量级？

从 Python 与 C 的矩阵乘法出发，沿着循环顺序、缓存分块、Roofline 和 FMA，分析同一计算在不同硬件上的性能差异。
LEEcDiangChengzhan Li 2026.11.03 发布

同样计算两个双精度矩阵，Python 的一行 A @ B 有时能跑赢 C 的三重循环。沿着这两段代码看看，时间究竟花在取数据、执行指令，还是等待上一次乘加。

为什么 Python 有时比 C 还快？

如果让 Python 和 C 分别计算两个 1024×1024 的双精度矩阵乘法，哪个更快？

直觉上应该是 C。它是编译型语言，能够直接生成机器码，省去了 Python 解释器的运行时开销。但如果我们用 Python 的 NumPy 实现矩阵乘法，再拿它和一段普通的 C 三重循环比较，结果很可能反过来：Python 代码更快，甚至可能快出几个数量级。

差别出在执行乘加的那段代码上。

Python 的 A @ B 可能直接进入针对特定处理器高度优化的 BLAS 库；C 的三重循环则可能生成访存效率很差的标量指令。前者让硬件的大部分时间用于计算，后者可能让处理器一直等待数据。

这引出了一个比“哪种编程语言更快”更有意思的问题：同一项计算任务，是怎样被映射到一台计算机上的？哪些性能差异来自语言，哪些来自软件实现，又有哪些实际上由硬件架构决定？

矩阵乘法恰好适合回答这些问题。它的数学定义非常简单，但围绕它的性能优化，已经发展出一整套关于数据复用、缓存、向量化和专用加速器的工程方法。

一、先确定我们究竟在计算什么

考虑两个 N×N 的矩阵：

C=AB,Cij=∑k=0N−1AikBkj

以下讨论统一采用 IEEE 754 双精度浮点数（FP64），每个元素占据 8 Byte，使用传统的矩阵乘法算法，而不是 Strassen 等改变运算复杂度的方法。

计算一个输出元素需要约 N 次乘法和 N 次加法，因此整个计算的浮点运算量通常记为：

F≈2N3 FLOP

当 N=1024 时：

F=2×10243≈2.147×109 FLOP

二、语言的性能差异，究竟发生在哪一层？

一段源代码要变成处理器能够执行的计算，通常需要经过多个层次。

可以把它拆成三个问题：第一，语言运行时如何执行程序？第二，编译器或数值库生成了怎样的指令？第三，实际的指令和数据访问方式是否适合硬件？

例如，一个使用 OpenBLAS 的 Python 程序和一个调用同一版本 OpenBLAS 的 C 程序，如果输入布局、线程配置和调用方式相同，它们进入的计算内核可以是同一段机器码。在足够大的矩阵乘法中，Python 与 C 的函数调用开销相对于实际计算时间可能很小。

反过来，即使 C 已经编译为原生机器码，也不意味着其生成的内存访问模式和指令组合一定高效。

这里还涉及一个容易被忽视的区别：语言语义与语言实现并不是一回事。

编程语言规定了程序应当表现出什么行为，但并不总是规定这些行为必须如何在硬件上实现。编译器、运行时、标准库以及具体的程序结构，都可以影响最后的执行效率。

对于计算密集型程序，类型信息、数据是否连续、内存是否可能发生别名、编译器能否证明循环之间没有依赖，往往比源代码采用哪种语法更加重要。

三、同样是 C，为什么交换两层循环就能变快？

现在我们暂时离开 Python，把问题限制在 C 内部。

假设矩阵按 Row-major（行优先）顺序连续存储。对于二维矩阵 A，元素 A[i][j] 在一维内存中的地址偏移为：

offset(i,j)=iN+j

这意味着相邻列元素在内存中相邻，而相邻行元素相隔 N 个元素。

1. 最直观的 i-j-k 循环

观察最内层循环。

当 k 增加时，A[i*N+k] 在内存中连续移动，每次前进 8 Byte；但 B[k*N+j] 每次跨越一整行，地址前进 8N Byte。

如果 N=1024，那么访问 B 的步长就是 8192 Byte。

这对于缓存和预取机制并不友好。以常见的 64 Byte Cache Line 为例，一条缓存线能够容纳 8 个 FP64 元素，但跨行访问可能让程序每次只使用其中很少的一部分。更重要的是，在较大的矩阵上，B 中的数据可能在下一次被使用之前就已经被缓存替换。

2. 改成 i-k-j 循环

两段程序执行的都是传统矩阵乘法，复杂度同样为 O(N3)。

但是现在，最内层的 j 遍历 B 的一整行：

相应的 C 元素也被连续更新。A[i,k] 则被提取为一个标量，在内层循环中反复使用。

这样处理后，硬件预取器更容易识别访问模式，编译器也更容易对连续数据进行 SIMD 向量化。

当然，i-k-j 不是所有硬件和矩阵尺寸下必然最快的循环顺序。它会反复读写 C，若 C 的活跃部分不能留在缓存中，仍然存在额外开销。对于列优先存储的 Fortran 数组，合适的循环顺序也会有所不同。

两段循环做了同样多的乘加。交换循环顺序，改变的是下一次访问能否用上刚取进缓存的数据。

四、Blocking：让数据在离开缓存之前多做几次计算

循环重排改善了访问的连续性，但还没有完全解决数据复用问题。

对于矩阵乘法，A 的一个元素会参与多个输出元素的计算，B 的一个元素也会被反复使用。如果每次需要它们时都重新从较慢的存储层读取，处理器的大部分能力就可能浪费在等待数据上。

更系统的解决办法是 Cache Blocking，也称 Tiling。

1. 把大矩阵分成小矩阵

我们把矩阵分成多个 T×T 的块，对每一组块计算：

Ctile+=AtileBtile

这样，一个 A 子块与 B 子块进入缓存后，就能完成一批乘加运算，而不是只贡献给某一个输出元素。

因此，Tile Size 通常不是一个越大越好的参数。合适的值需要结合处理器的缓存层次、向量寄存器和实际矩阵形状确定。

2. 继续向下：寄存器级 Micro-kernel

高性能 BLAS 库通常不满足于 Cache Blocking。

它们还会将 A、B 的部分数据打包（Packing）为适合微内核运算的连续布局，然后在寄存器中保留一个很小的 C 子块。

微内核可以抽象为：

在理想情况下，C 子块在多轮 FMA 中始终保留在寄存器内，减少反复 Load/Store；A 和 B 的数据通过向量寄存器广播或加载，反复参与多个输出元素的计算。

2008 年，Goto 与 van de Geijn 在经典论文 Anatomy of High-Performance Matrix Multiplication 中系统解释了如何围绕多级内存层次组织 GEMM。此后的 BLIS、OpenBLAS 等实现继承并发展了这套思想。

现代 GEMM 往往可以拆解为多层循环、数据打包过程以及一个与硬件紧密相关的 Micro-kernel。

这实际上是一种软硬件共同设计的分层结构：外层循环负责大规模任务分解与缓存复用；Packing 负责把原始矩阵转换为适合微内核的数据布局；Micro-kernel 负责寄存器复用、SIMD/FMA 指令和计算流水线利用。

编程语言负责表达计算，编译器和数值库则负责把这个计算映射到合适的数据流和指令序列。

五、用 Roofline 模型判断：我们究竟缺算力还是缺带宽？

到这里，我们一直在说“缓存命中率更高”“数据复用更充分”，但还缺少一个能够把这些因素量化的模型。

Roofline Model 正是为此提出的。

Williams、Waterman 和 Patterson 提出了这个性能模型，把处理器的计算上限、内存带宽和程序的数据移动量联系在一起 [2]。

核心关系为：

Pattainable≤min(Ppeak,Bmemory×I)
符号 物理含义 单位
Pattainable 可达到的浮点计算吞吐 FLOP/s
Ppeak 处理器峰值浮点吞吐 FLOP/s
Bmemory 可持续内存带宽 Byte/s
I Operational Intensity FLOP/Byte

这里的 Operational Intensity 是单位 DRAM 流量所对应的运算量。它不是简单地统计源代码里写了多少次数组访问，而是考虑经过缓存层次之后，真正到达主存的流量。

1. 矩阵乘法为什么适合高性能计算？

继续使用 N×N 的 FP64 矩阵。

如果假设输入最初不在缓存中、每个 A 和 B 元素都只从主存读取一次、每个 C 元素最终只写回一次，并忽略写分配等额外流量，那么：

Dideal=8N2+8N2+8N2=24N2 Byte

代入传统矩阵乘法的运算量：

Iideal=2N324N2=N12FLOP/Byte

以 N=1024 为例，理想流量约为 24 MiB，对应约 85.33 FLOP/Byte。

这意味着：如果数据复用足够有效，处理器每从 DRAM 搬运一个字节，就有机会完成相当多的浮点运算。

这不是说矩阵变大就一定更快，更不能认为真实程序一定能达到这些数据流量下限。

尤其是在缓存较小、分块不当或大量重复访问的实现里，实际 DRAM 流量可能远大于上述估算。另一方面，如果数据已经驻留缓存，重复测试时的 DRAM 流量又可能低于冷启动假设。

它展示的是 GEMM 的一个重要潜力：计算量随 N3 增长，但理想数据流量只随 N2 增长。

2. 优化代码，实际上是在改变 Roofline 上的位置

一段低效的矩阵乘法程序，可能反复从主存加载相同的数据，使实际 Operational Intensity 很低。此时即使增加 SIMD 算力，程序也未必变快。

Blocking 与 Packing 改善数据复用后，程序可能获得更高的 Operational Intensity，从而逐渐摆脱主存带宽的限制。

当程序进入 Compute-bound 区域后，性能优化的主要方向才进一步转向 SIMD 利用率、FMA 吞吐、指令级并行和执行单元调度。

当然，Roofline 是上界模型，而非精确运行时间预测器。即使程序位于理论上的 Compute-bound 区域，也可能因为寄存器溢出、依赖链、指令前端瓶颈或负载不均衡而无法接近峰值。

所以优化需要同时考虑两个方向：减少不必要的数据移动，以及让已经抵达计算单元的数据被充分利用。

六、当我们把优化推到极致，就开始接触计算机体系结构

前面讨论的大部分优化看起来还属于软件工程，但它们对应的需求几乎都能在现代处理器中找到硬件上的回应。

1. SIMD：既然数据连续，为什么不一次计算多个？

考虑一个具有 256-bit 向量寄存器的处理器。

一个 FP64 元素占 64 bit，因此一个向量寄存器能够容纳 4 个 FP64 元素。

如果硬件支持相应的向量 FMA 指令，就可能在一条向量指令中完成：

C0:3←A0:3×B0:3+C0:3

按照每次乘法与加法分别记为一个 FLOP 的约定，这相当于 8 FLOP。

但拥有 SIMD 指令集，不代表任何循环都会自动使用它。

编译器通常需要确认：数据访问足够规则，操作之间不存在妨碍向量化的依赖，内存别名不会破坏结果，并且向量化收益能够抵消额外的控制和数据整理成本。

这也解释了为什么循环重排、数据类型和 restrict 等信息能够影响最终代码，即使 CPU 的 ISA 完全没有变化。

当一个 GEMM 内核已经相当高效时，一次有意义的改进可能只有几个百分点。其价值在于找到此前没有充分利用的硬件资源，而不是重新发明矩阵乘法算法。关于实际处理器上的具体性能数据，应直接参考厂商原文，而不是把不同测试环境的数字拼成一张图。

3. 存储层次：Cache 不是越大越好

从程序员的视角看，我们希望缓存尽可能大，数据离计算单元尽可能近。

但从芯片设计的角度看，容量、面积、功耗和访问延迟之间存在真实的权衡。

更大的缓存可能提高数据命中率，却也可能增加访问延迟和芯片面积。更宽的向量执行单元能提高理论吞吐，但需要更高的数据供给能力、更复杂的寄存器文件及配套数据通路。

多核共享缓存还涉及带宽争用、缓存一致性、NUMA 和线程调度。

因此，计算机体系结构并不是简单地不断增加 ALU、FMA 或缓存容量，而是让计算资源、数据供给能力与目标工作负载相匹配。

4. 从 CPU 到 GPU，再到专用矩阵加速器

当 GEMM 被不断优化，我们会发现大量计算都围绕相同的规律展开：一个输入元素需要被多个乘法器反复使用，输出结果需要在多次累加之间保留，而外部内存访问应该尽可能少。

这也是为什么矩阵计算可以进一步映射到 GPU 的线程块、Shared Memory、寄存器分块以及专用的矩阵乘法指令。

以 NVIDIA A100 为例，它不仅提供常规 FP64 执行能力，也提供支持 FP64 矩阵运算的 Tensor Core 路径。NVIDIA 公布的相关峰值分别为 9.7 TFLOP/s 和 19.5 TFLOP/s [7]。

这里需要特别区分精度：并不是所有 GPU 都具备强大的 FP64 吞吐，也不是所有 Tensor Core 都支持同等意义的 FP64 运算。消费级 GPU 的 FP32/FP16 峰值，不能直接拿来估算 FP64 DGEMM 性能。

对于适合规则数据流的矩阵运算，专用硬件还可以进一步采用 Systolic Array 等架构，让操作数沿着计算单元阵列传播，在局部完成多次乘加。

CPU 上的 Blocking 是在软件中安排数据复用；专用加速器则可以把这种复用关系直接组织成片上 SRAM、寄存器和计算单元之间的硬件数据流。

从这个意义上说，矩阵加速器不是单纯把乘法器堆得更多，而是将算法的数据移动规律固化或半固化为硬件结构。

七、从程序优化反推芯片设计：我们究竟应该加速什么？

如果只从 ISA 的角度理解计算机，很容易认为性能提升主要来自新指令、更大的向量宽度或更高的时钟频率。

但通过 DGEMM，我们可以建立一个更完整的对应关系：

软件中发现的问题 体系结构中的对应设计
逐元素操作的调度开销很高 向量指令、专用矩阵指令、低开销执行模型
相同数据反复从主存加载 多级 Cache、Scratchpad SRAM、数据复用
访存不连续 Cache Line、预取器、连续访问与合并访存
FMA 之间存在串行依赖 多累加器、流水线、指令级并行
多线程争用共享资源 缓存分层、内存通道、NUMA、调度机制
大规模数据搬运限制效率 更高带宽、局部存储、计算与搬运重叠

假设我们准备在 FPGA 上实现一个矩阵乘法加速器。

首先增加乘法器数量，当然可能提高峰值计算能力。但如果片外 DDR 无法及时提供操作数，新增乘法器就会长期处于空闲状态。

如果我们改为让输入数据先进入片上 BRAM，再通过分块与流水线多次复用，可能反而能在较少的计算资源下获得更高的实际吞吐。

不过，这又会引入新的问题：BRAM 端口数量是否足够？Banking 是否冲突？流水线能否达到目标 Initiation Interval？片上缓冲器的面积、功耗和布线代价是否合理？

软件中一次看似简单的 Blocking 优化，在硬件中就变成了存储组织、并行度与数据通路之间的设计问题。

体系结构设计的一个核心工作，就是为目标计算寻找合适的数据流，并决定用多少存储、多少算术单元和多少控制逻辑去支撑它。

这套思路也适用于 AI 推理中的矩阵乘法、Attention、卷积，以及许多其他高吞吐计算模块。

八、做性能实验时，怎样避免得出错误结论？

矩阵乘法是一个非常容易跑出漂亮数字、也非常容易比较失真的 Benchmark。

如果真要比较 Python、C、Rust、Julia 或不同 BLAS 后端，至少要确保工作负载和测量边界一致。

首先统一输入的维度、FP64 精度、存储布局和线程数量；再区分是否包含内存分配、JIT 首次编译、数据打包或 CPU/GPU 数据传输；之后才是计时与性能分析。

多次运行应报告中位数和离散程度，并保留编译器版本、编译选项及 BLAS 后端信息。下载附件中的 C 与 Python 脚本默认各重复 5 次，均输出原始样本、repeats、median_ms、iqr_ms、min_ms、max_ms、best_ms 和按中位耗时计算的 median_gflops。IQR 为第 75 与第 25 百分位数之差，按排序后位置 (n-1)×q 线性插值；best_ms 单独表示最小耗时。运行环境写入标准错误流，可与结果一并保存；附件 README 给出完整命令。对于 CPU，可以结合 perf 或其他性能计数器观察周期数、指令数、缓存行为和硬件资源利用情况。

计算吞吐通常使用：

GFLOP/s=2N3Tseconds×109

这个指标比单纯的加速比更容易与硬件计算能力建立联系，但它也不能替代总运行时间。

对于小矩阵，固定调用开销可能占据很高比例；对于大矩阵，缓存容量、内存带宽和计算单元吞吐逐渐成为主要因素。不同矩阵规模的性能排名可能变化，因此不能仅凭一个 N 值确定某种实现是否优秀。

还有一个数值语义问题。

浮点加法不满足严格的结合律，FMA 也可能改变中间舍入过程。因此，改变循环顺序、进行向量化或并行归约后，两段正确的 FP64 矩阵乘法程序未必产生逐位相同的结果。

性能测试应根据任务要求同时验证误差、数值稳定性及必要的可重复性，而不是默认“数学表达式相同”就等于“所有输出比特必须相同”。

九、结语：性能问题最终会回到计算与数据的关系

最初的问题是：为什么不同编程语言实现相同的矩阵乘法，会出现巨大速度差异？

语言和运行时决定计算如何进入执行系统；编译器与数值库决定如何组织循环、指令和数据；微架构则决定这些指令能够以怎样的吞吐执行，以及数据能以多大的带宽和多低的延迟抵达计算单元。

同一种语言内部，我们可以通过改变数据布局、循环顺序、分块策略、向量化方式和并行度，显著提高性能。但优化并不是永远有效的。每解决一个瓶颈，都可能遇到下一个瓶颈。

解释器开销降低后，可能发现缓存访问低效；缓存利用改善后，可能发现 SIMD 没有充分使用；计算单元利用率提高后，又可能受制于内存带宽、功耗或线程扩展效率。
