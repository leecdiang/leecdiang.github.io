同样的矩阵乘法，为什么能差几个数量级？

矩阵乘法的性能差异来自语言执行开销、循环顺序、缓存复用与硬件映射。结合分块、Roofline 和 FMA，分析同一计算如何受到不同资源约束。
LEEcDiangChengzhan Li 2026.11.03 发布

同一 FP64 矩阵乘法中，NumPy 的 A @ B 可能显著快于普通 C 三重循环。差异来自实际执行路径：解释器与本地库的职责划分、循环和数据布局，以及缓存、SIMD/FMA 与执行流水线的利用。本文以这些关系为线索，讨论程序优化如何对应到体系结构约束。

Python 标量循环与数值库调用

对于两个 1024×1024 双精度矩阵的乘法，直接比较 Python 与 C 的语言名称，并不足以预测运行时间。

C 的原生编译避免了解释器逐步执行的开销，但 NumPy 与普通 C 循环可能调用完全不同的计算内核。在合适的实现和规模下，前者可能获得数量级的性能优势。

这一比较首先需要确定实际承担乘加运算的代码。

A @ B 通常可以进入针对处理器优化的 BLAS；普通 C 三重循环则可能生成标量指令和低效访存。前者将调用开销摊销到大规模本地计算中，后者即使没有解释器开销，也可能受数据供给限制。

性能分析因此需要区分语言运行时、算法实现与硬件执行三层因素。本文逐项考察循环、数据组织和指令调度怎样影响计算资源利用，并说明这些变化为何不能简单归因于语言优劣。

矩阵乘法具有明确的数学工作量，又能体现数据复用、缓存分块、向量化和专用计算结构，适合在固定任务下比较这些实现选择。

一、固定计算任务与精度

考虑两个 N×N 的矩阵：

C=AB,Cij=∑k=0N−1AikBkj

以下讨论统一采用 IEEE 754 双精度浮点数（FP64），每个元素占据 8 Byte，使用传统的矩阵乘法算法，而不是 Strassen 等改变运算复杂度的方法。

计算一个输出元素需要约 N 次乘法和 N 次加法，因此整个计算的浮点运算量通常记为：

F≈2N3 FLOP

当 N=1024 时：

F=2×10243≈2.147×109 FLOP

二、语言运行时与数值内核的性能边界

源代码到机器执行之间，编译器、运行时与数值库分别参与语义实现、指令生成和计算组织。

分析时应分别核查运行时承担的工作、编译器或库生成的指令，以及这些指令和访问模式对硬件的适配程度。

Python 和 C 若调用同一版本 OpenBLAS，并保持输入布局、线程和调用条件一致，可能进入相同机器码内核。对足够大的矩阵，入口调用成本相对于计算时间的占比可以很低。

原生机器码只消除了部分语言开销，并不保证访存次序或指令组织有效。

语言语义规定可观察行为，语言实现决定这些行为如何映射到执行系统。

编译器、运行时、标准库和程序结构均会改变执行成本。因此，单一实现的测量结果不能直接作为语言语义的性能属性。

对计算密集任务，类型是否明确、数据是否连续、是否存在内存别名、编译器能否证明循环没有依赖，往往更直接地影响执行效率。

三、循环顺序与连续内存访问

固定为 C 实现后，仅改变循环次序，也可以改变缓存和预取行为。

假设矩阵按 Row-major（行优先）顺序连续存储。对于二维矩阵 A，元素 A[i][j] 在一维内存中的地址偏移为：

offset(i,j)=iN+j

这意味着相邻列元素在内存中相邻，而相邻行元素相隔 N 个元素。

1. i-j-k 循环的访问模式

最内层循环决定连续两次访问之间的地址步长。

当 k 增加时，A[i*N+k] 在内存中连续移动，每次前进 8 Byte；但 B[k*N+j] 每次跨越一整行，地址前进 8N Byte。

如果 N=1024，那么访问 B 的步长就是 8192 Byte。

一条常见的 64 Byte Cache Line 可容纳 8 个 FP64 元素。跨行访问 B 时，单次搬入的数据可能只被部分使用；工作集较大时，数据还可能在下次复用前被替换。这降低了缓存线利用率，也增加了预取难度。

2. i-k-j 循环的访问模式

两段程序执行的都是传统矩阵乘法，复杂度同样为 O(N3)。

但是现在，最内层的 j 遍历 B 的一整行：

相应的 C 元素也被连续更新。A[i,k] 则被提取为一个标量，在内层循环中反复使用。

连续访问有利于硬件预取，也更容易满足编译器生成 SIMD 指令所需的规则访问条件。

i-k-j 同时增加了对 C 的反复更新；若活跃区域无法驻留缓存，仍会产生额外读写。因此，最佳次序依赖矩阵规模与存储层次。列优先 Fortran 数组的连续方向不同，优化次序也应相应调整。

循环重排不减少乘加次数，而是改变数据复用距离和缓存线使用方式。其收益来自访存组织，而非算法复杂度下降。

四、Blocking：围绕存储层次组织数据复用

连续访问改善空间局部性，但不保证反复使用的数据能够持续驻留缓存。

A、B 的元素均参与多个输出。若复用间隔超过缓存可容纳的工作范围，程序仍需反复从较慢层级读取相同数据，限制计算吞吐。

Cache Blocking（Tiling）通过分解工作集，缩短复用距离，使一组数据在被替换前完成更多运算。

1. 缓存分块

我们把矩阵分成多个 T×T 的块，对每一组块计算：

Ctile+=AtileBtile

A、B 子块进入缓存后用于更新一批输出，以提高同一次数据搬运所支撑的乘加数量。

2. 寄存器级 Micro-kernel

高性能 BLAS 还会进一步组织寄存器级复用。

Packing 将 A、B 的部分数据转换为适合微内核读取的连续布局，Micro-kernel 则将小规模 C 子块保留在寄存器中累加。

微内核可以抽象为：

理想情况下，C 子块在多轮 FMA 中驻留寄存器，减少 Load/Store；A、B 通过加载或广播进入向量寄存器，再用于多个输出。寄存器容量与指令调度共同限制这一复用范围。

2008 年，Goto 与 van de Geijn 在经典论文 Anatomy of High-Performance Matrix Multiplication 中系统解释了如何围绕多级内存层次组织 GEMM。此后的 BLIS、OpenBLAS 等实现继承并发展了这套思想。

现代 GEMM 因而通常由多层循环、数据打包和硬件相关的 Micro-kernel 组成。

外层循环安排任务分解与缓存复用，Packing 适配数据布局，Micro-kernel 组织寄存器复用、SIMD/FMA 和执行流水线。各层分别对应不同距离和容量的数据供给约束。

相同的语言表达可以进入不同的数据流和指令序列，数值库对这些层次的组织，是性能差异的重要来源。

五、用 Roofline 估计算力与带宽的约束

缓存命中与数据复用还需要转换为可量化的计算、带宽约束。

Roofline 使用运算量与实际数据流量建立这种对应。

Williams、Waterman 和 Patterson 提出了这个性能模型，把处理器的计算上限、内存带宽和程序的数据移动量联系在一起 [2]。

核心关系为：

Pattainable≤min(Ppeak,Bmemory×I)
符号 物理含义 单位
Pattainable 可达到的浮点计算吞吐 FLOP/s
Ppeak 处理器峰值浮点吞吐 FLOP/s
Bmemory 可持续内存带宽 Byte/s
I Operational Intensity FLOP/Byte

此处 Operational Intensity 以实际 DRAM 流量为分母。源码中的数组访问次数不能直接代替该流量，因为缓存已经吸收了部分访问。

1. GEMM 的运算强度与数据复用

继续使用 N×N 的 FP64 矩阵。

如果假设输入最初不在缓存中、每个 A 和 B 元素都只从主存读取一次、每个 C 元素最终只写回一次，并忽略写分配等额外流量，那么：

Dideal=8N2+8N2+8N2=24N2 Byte

代入传统矩阵乘法的运算量：

Iideal=2N324N2=N12FLOP/Byte

以 N=1024 为例，理想流量约为 24 MiB，对应约 85.33 FLOP/Byte。

在这一理想流量假设下，DRAM 每传输一个字节能够支撑较多浮点运算，反映了矩阵乘法的数据复用潜力。

它展示的是 GEMM 的一个重要潜力：计算量随 N3 增长，但理想数据流量只随 N2 增长。

2. 代码优化与 Roofline 约束变化

重复读取主存会降低实际 Operational Intensity。此时提高 SIMD 峰值，未必改变限制程序吞吐的带宽约束。

Blocking 与 Packing 若减少主存流量，可以提高 Operational Intensity，并使计算更接近执行资源给出的上界。

进入 Compute-bound 区域以后，SIMD 利用率、FMA 吞吐、指令级并行和执行端口调度才更可能成为主要优化对象。

Roofline 仍是上界模型。寄存器溢出、依赖链、前端供给不足或负载不均衡，均可能使实际性能低于 Compute-bound 区域的理论上限。

数据移动成本与执行资源利用需要同时测量，单独改善其中一项并不足以保证接近峰值。

六、软件优化对应的微架构约束

循环、布局与微内核的优化，最终受向量宽度、寄存器容量、执行流水线和存储层次限制。

1. SIMD 的数据与依赖条件

考虑一个具有 256-bit 向量寄存器的处理器。

一个 FP64 元素占 64 bit，因此一个向量寄存器能够容纳 4 个 FP64 元素。

如果硬件支持相应的向量 FMA 指令，就可能在一条向量指令中完成：

C0:3←A0:3×B0:3+C0:3

按照每次乘法与加法分别记为一个 FLOP 的约定，这相当于 8 FLOP。

SIMD 指令可用，并不意味着编译器一定能够对目标循环向量化。

编译器需要证明访问规律、迭代依赖与内存别名允许向量执行，还需评估控制和数据整理开销是否抵消收益。

这也解释了为什么循环重排、数据类型和 restrict 等信息能够影响最终代码，即使 CPU 的 ISA 完全没有变化。

成熟内核的改进幅度可能仅为几个百分点，对应此前未被充分利用的资源。具体性能需要依据厂商测试条件解释，不能将不同平台、规模与线程设置下的数字直接组合比较。

3. 缓存容量、命中率与访问代价

缓存容量影响复用机会，但仍需与访问时间和实现代价一起评估。

增加容量可能增加面积、功耗和访问延迟，不能将命中率改善单独等同于程序加速。

更大的缓存可能提高数据命中率，却也可能增加访问延迟和芯片面积。更宽的向量执行单元能提高理论吞吐，但需要更高的数据供给能力、更复杂的寄存器文件及配套数据通路。

多核共享缓存还涉及带宽争用、缓存一致性、NUMA 和线程调度。

计算资源与存储容量应围绕目标工作负载配置，使执行吞吐和数据供给保持匹配。

4. CPU、GPU 与矩阵加速器的执行结构

GEMM 的数据流需求包括输入复用、跨多次累加保留输出，以及减少外部内存流量。不同处理器通过不同的资源组织满足这些需求。

GPU 将其映射到线程块、Shared Memory、寄存器分块和专用矩阵指令。

以 NVIDIA A100 为例，它不仅提供常规 FP64 执行能力，也提供支持 FP64 矩阵运算的 Tensor Core 路径。NVIDIA 公布的相关峰值分别为 9.7 TFLOP/s 和 19.5 TFLOP/s [7]。

上述数值只对应 A100 的 FP64 路径。不同 GPU 的 FP64 吞吐、Tensor Core 精度支持均可能不同，消费级 FP32/FP16 峰值不能直接用于估算 FP64 DGEMM。

对于适合规则数据流的矩阵运算，专用硬件还可以进一步采用 Systolic Array 等架构，让操作数沿着计算单元阵列传播，在局部完成多次乘加。

CPU 上的 Blocking 是在软件中安排数据复用；专用加速器则可以把这种复用关系直接组织成片上 SRAM、寄存器和计算单元之间的硬件数据流。

矩阵加速器因此需要同时组织算术单元与局部数据流，乘法器数量不能独立决定有效吞吐。

七、从 DGEMM 数据流到 FPGA 结构设计

新增指令、向量宽度和频率描述计算能力，却不能单独说明操作数能否持续到达。

表中将 DGEMM 的优化需求对应到具体硬件资源。

软件中发现的问题 体系结构中的对应设计
逐元素操作的调度开销很高 向量指令、专用矩阵指令、低开销执行模型
相同数据反复从主存加载 多级 Cache、Scratchpad SRAM、数据复用
访存不连续 Cache Line、预取器、连续访问与合并访存
FMA 之间存在串行依赖 多累加器、流水线、指令级并行
多线程争用共享资源 缓存分层、内存通道、NUMA、调度机制
大规模数据搬运限制效率 更高带宽、局部存储、计算与搬运重叠

假设我们准备在 FPGA 上实现一个矩阵乘法加速器。

增加乘法器提高理论峰值；若片外 DDR 无法提供足够操作数，新增单元仍受数据供给限制。

将输入缓冲到片上 BRAM，并结合分块与流水复用，可能在较少算术资源下获得更高实际吞吐。

该方案仍需核查 BRAM 端口、Banking 冲突、目标 Initiation Interval，以及缓冲的面积、功耗和布线成本。

Blocking 在硬件中的实现，涉及存储组织、并行度和数据通路的联合设计。

数据流确定后，存储容量、算术单元和控制逻辑仍需要共同配置，避免局部资源扩张将瓶颈转移到其他模块。

这套思路也适用于 AI 推理中的矩阵乘法、Attention、卷积，以及许多其他高吞吐计算模块。

八、性能实验的控制条件与测量误差

矩阵乘法的加速比容易受到数据结构、线程数和计时边界影响。

比较 Python、C、Rust、Julia 或不同 BLAS 后端，应首先对齐任务和测量条件。

输入维度、FP64 精度、布局和线程数应保持一致；分配、JIT 首次编译、Packing 与 CPU/GPU 传输是否计时也应明确。否则，测量差异无法归因到目标实现。

多次运行应报告中位数和离散程度，并保留编译器版本、编译选项及 BLAS 后端信息。下载附件中的 C 与 Python 脚本默认各重复 5 次，均输出原始样本、repeats、median_ms、iqr_ms、min_ms、max_ms、best_ms 和按中位耗时计算的 median_gflops。IQR 为第 75 与第 25 百分位数之差，按排序后位置 (n-1)×q 线性插值；best_ms 单独表示最小耗时。运行环境写入标准错误流，可与结果一并保存；附件 README 给出完整命令。对于 CPU，可以结合 perf 或其他性能计数器观察周期数、指令数、缓存行为和硬件资源利用情况。

计算吞吐通常使用：

GFLOP/s=2N3Tseconds×109

GFLOP/s 便于与执行资源吞吐对照，总运行时间则反映任务完成成本，两项指标应同时保留。

小矩阵可能由固定调用成本主导，大矩阵则更多受到缓存、带宽和计算吞吐约束。单一 N 下的性能次序，不能直接推广到其他规模。

计算结果的数值语义也属于实验条件。

浮点加法不满足严格的结合律，FMA 也可能改变中间舍入过程。因此，改变循环顺序、进行向量化或并行归约后，两段正确的 FP64 矩阵乘法程序未必产生逐位相同的结果。

正确性验证应依据任务要求检查误差、稳定性和可重复性，并明确是否要求逐位一致。

九、执行路径与瓶颈迁移

NumPy 快于普通 C 循环的现象，应根据实际内核与数据路径解释。

运行时决定任务如何交给执行系统，编译器与数值库决定指令和数据组织，微架构则决定可达到的吞吐、带宽和延迟。三层约束共同形成运行时间。

同一语言可以通过布局、循环、分块、向量化和并行度改变性能，但一次局部优化的收益依赖其对应约束仍占主要比例。

解释器开销降低后，缓存访问可能成为限制；访存改善后，SIMD 与执行单元利用可能成为限制。更高计算利用率又可能增加带宽、功耗或线程扩展压力，因此优化后需要重新测量并检查瓶颈迁移。
