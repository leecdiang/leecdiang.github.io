为什么我觉得 X86 指令集 就是一坨狗屎

从不规则指令编码、历史兼容性和 x86S 提案的搁置，谈 x86 的真实工程代价，以及世界转向多架构的可能。
LEEcDiangChengzhan Li 2026.11.04 发布

假如你接手了一个迭代四十多年的 RTL 仓库，每次升级都不敢删除旧逻辑，状态机、旁路条件和兼容分支越堆越多，你会怎么评价它？

我大概会说：这玩意儿早该重构了。

x86 难以重构，恰恰因为它太成功了。它诞生于 1978 年的 Intel 8086，后来装进了 PC、服务器、工作站，建立了规模惊人的软件生态。今天的高性能 x86 处理器早已不是四十年前那颗芯片，它们可以拥有宽大的乱序后端、复杂的分支预测、向量计算和先进封装。但在这些精致的工程之上，仍然压着一套漫长历史留下的架构契约。S01 S05

最妙的是，连 Intel 都试过动这份契约。它在 2023 年提出精简 x86 的 x86S，后来却决定不再推进。2024 年，Intel 和 AMD 又联合产业伙伴组建了 x86 生态咨询组，准备一起协调这套 ISA 的未来。S05 S06

标题骂得难听。我佩服能把 x86 做得这么快的工程师，反感的是他们每设计一代新芯片，都得替旧软件再背一次兼容性的包袱。我想知道，这笔账到底有多大。哪些约束已经有了更简单的替代方案，却仍然退不掉？

我说 x86 落后，指的是它让今天的设计者仍须兑现几十年前的承诺。最直观的例子就在按下电源键之后。现代系统最终要在 64 位模式下运行，处理器却得先按 8086 的规矩醒来，再靠启动代码切过去。Intel 提议过让新处理器直接从 64 位状态启动，后来根据生态反馈收回了方案。S05

从四个字节开始，理解 x86 为什么难伺候

翻开 x86 指令手册，最让人头疼的不是指令数量，而是连下一条指令从哪里开始，都要先解析当前指令。

x86-64 的指令可以长 1 到 15 Byte。它可能带有传统前缀、REX 前缀，也可能采用 VEX、EVEX 等扩展编码；寻址与操作数又可能需要 ModR/M、SIB、位移量和立即数。APX 还引入了 REX2。字段的位置和长度由指令类别与执行模式决定。S02

AArch64 的 A64 指令则统一是 32 bit，也就是 4 Byte。处理器沿着指令流取出四个字节，天然就知道下一条从哪里开始。RISC-V 的基础指令为 32 bit，常见的 RV64GC 又引入 16 bit 压缩指令：需要判断 2 Byte 还是 4 Byte，但它从一开始就为这种长度变化留好了编码结构。严格说，RISC-V 规范还允许更长的格式，不能把整个 RISC-V 家族说成永远只有两种长度。S03 S04 S18

图 2 · 按 Intel XED、Arm 官方文档与 RISC-V 规范绘制的指令长度。x86 为定义的范围，RISC-V 显示 RV64GC 常见的 2/4 Byte，并不表示整体复杂度倍数。[S02] [S03] [S18]

这张图不能解读成“x86 的解码器有 ARM 的十五倍大”。字节长度不是门数，也不是功耗。它指出的是一种非常具体的工程差别：A64 的指令边界由定长编码直接给出，x86 的长度、前缀和操作数解释则彼此纠缠。

让前端一次处理多条 x86 指令，难点就跟着出现了。前端从缓存拿到一批字节，要划分指令边界、处理跨边界指令，再识别编码与操作数。做得越宽，并行处理这些不规则边界的压力越大。现代 x86 核心当然有办法：长度预译码、复杂解码器、微操作缓存，以及不同实现各自积累的技巧。但这些技巧本身也需要设计、验证和维护。S02

麻烦不只在译码器，还有那些舍不得删的历史

如果 x86 只是变长编码，我还不会用这么狠的标题。真正让人难受的，是从 8086、286、386 一路延伸过来的运行模式与架构状态。

早年的 16 位实模式、分段寻址、保护模式、32 位兼容性，再到后来的 x86-64 long mode，让 x86 形成了一张层层叠加的历史地图。x87 浮点栈、各代 SIMD 扩展、不同的前缀语义，又让这张地图不断向外扩张。注意，这不等于“Windows 11 现在还可以直接运行所有 DOS 程序”：操作系统能运行什么，与硬件保留了哪些历史机制，是两回事。S05

Intel 当年提出 x86S，理由已经够说明问题了：64 位操作系统成为主流后，一部分遗留模式在现代系统中几乎只用于启动过渡，值得考虑移除。它的草案想删掉部分 16/32 位特权与运行模式，同时保留 long mode 下的 32 位应用兼容子模式。也就是说，Intel 提议的都不是“立刻砸碎全部旧软件”，而是一次相当克制的清理。S05

可连这一步都没走成。Intel 最终宣布不继续推进 x86S，并强调继续维护软件兼容性。大约同一阶段，Intel、AMD 和产业伙伴开始通过 x86 生态咨询组讨论更一致的架构接口。S05 S06

工程师也许愿意删掉这些旧功能，卖芯片的人却很难点头。某家公司的固件、某套企业虚拟化环境、某个靠老二进制维生的业务，只要还在，厂商就必须认真考虑它。存量软件从外部给芯片设计施加约束，硬件也不能简单地宣布“从今天起不兼容了”。

你可以在 RTL 里清掉一段死逻辑，却没法轻易清掉全球用户对一条 ISA 的预期。

Intel 和 AMD 到底为这套包袱花了多少钱？

我想知道，两家公司一年究竟花多少钱维护 x86 兼容性。先看财报能回答到哪一步。

Intel 的 2025 年报写明，当年的研发费用为 138 亿美元；AMD 的同期研发费用为 80.91 亿美元。加起来约 218.91 亿美元。这笔钱涵盖了制程、封装、CPU、GPU、AI 加速器、FPGA、软件以及其他研究方向。财报没有把“维护 x86 旧模式、旧指令和相关验证”单独拆出来。S07 S08

所以，谁要是拿这 219 亿美元说“都浪费在 x86 上了”，我反而不会相信。Intel 的工艺节点与晶圆厂问题，AMD 的 GPU、AI 和软件投入，显然不能直接扣到 x86 ISA 的头上。

不过，有些成本确实随着这套架构一直存在，而且能明确指出工作发生在哪儿：

  • 指令前端。 处理变长指令、前缀、跨界和罕见编码，还要在高吞吐、低延迟与低功耗之间做设计选择。
  • 功能验证。 旧模式、异常、特权切换、虚拟化、指令扩展之间的交互，需要规格、测试与回归；软件可以观察到的行为，不能随便改。
  • 固件与操作系统。 启动路径、特性枚举、微码更新、ABI 及虚拟化兼容，都需要厂商和系统软件合作。
  • 产品迭代。 一部分工程人力持续用于确保“旧程序还是对的”，而不是完全投入新指令、新执行模型或更简单的硬件接口。

这些是可识别的工程负担，但公开信息不足以给它们合计出可信的金额。即便某家厂商明天宣布采用 A64，做新芯片仍然需要微架构、工具链、验证和操作系统团队；也不能把从前的所有前端成本都当作可节约项。

功耗上倒是有一份值得看的实验

2016 年的 USENIX CoolDC 论文试着专门激活 x86-64 的解码路径。在微基准超出已解码指令缓存容量的条件下，作者通过封装 RAPL 功耗测量与回归模型，估计解码器消耗了封装功耗的 3%–10%。S09

图 6 · 2016 年 CoolDC 论文估计，当 decoded-instruction cache 被突破时解码器占封装功耗约 3%–10%。不是现代芯片的通用范围，也不能据此计算换 ISA 的节能率。[S09]

我喜欢这份实验，是因为它真的把问题推进到了测量层面。可它并没有证明“换成 ARM 就立刻省下 10% 的整机功耗”：这是一项 2016 年特定平台、特定工作负载下的估计范围，也没有进行保持核心其余设计不变的跨 ISA 替换实验。

从工程视角看，我更在意被这份规范占据的设计空间。假如少了一批旧运行模式和不规则指令，前端能简化到什么程度？验证矩阵能缩小多少？是否能用更简单的规则提高取指和解码吞吐？答案得靠具体设计和测量，而不是靠 ISA 名字猜。

那 ARM 为什么看起来那么香？

Apple Silicon 的出现，显然让这件事有了很强的现实感。Apple 在 2020 年正式启动 Mac 从 Intel 到自研 Arm 架构芯片的迁移，连编译器、通用二进制和翻译层的过渡方案都一起准备好了。用户后来看到的则是出色的性能、能效和整机体验。云服务器也已经可以在 x86 以外选择 Arm 平台。S20

但这不能导出一个漂亮的“RISC 天然比 CISC 省电”定理。Emily Blem 等人在《ISA Wars》中比较过 ARM、MIPS 与 x86 平台，发现它们代表的是不同的工程设计点，不能单凭 RISC/CISC 分类预测性能与能效。S10

现代 CPU 的电和晶体管大量花在缓存、预测、执行单元、乱序窗口、内存系统和互连上。制程、频率、电压、核心规模、操作系统策略、内存与 SoC 集成方式都能改写最终结果。Apple 的优秀产品也包括这些因素，不能把功劳全给 A64 的 32 位定长编码。

AArch64 自身当然也不是一本永远保持极简的教科书。SVE、SME、虚拟化、安全特性和各种系统寄存器都在扩充它的架构规模。RISC-V 也并非不用付扩展兼容的账；模块化让它易于定制，同时要求软件与硬件对支持哪些扩展达成一致。S18 S19

但我仍觉得 A64 和 RISC-V 更适合作为未来新增设计的起点：它们有机会把历史功能取舍写进架构边界，而不是把四十年前的决定都视为理所当然。

假设全世界约好不再用 x86，会怎么样？

我当然希望看到这个平行宇宙。全世界的操作系统、编译器、云厂商、游戏工作室、芯片公司一起宣布：以后主力通用计算转向 AArch64 和成熟的 RISC-V 配置，新软件默认多架构发布，x86 留在隔离的兼容环境里慢慢退役。

最令人兴奋的并不是明天电脑突然快一倍，而是整个产业终于可以重新谈判软硬件之间的接口。CPU 公司不必把每一项新设计都安放在同一套历史状态之上，软件开发者也不用把 x86-64 当成唯一的桌面和服务器目标。硬件市场会更开放：Arm 芯片设计者围绕各自的 SoC 目标优化，RISC-V 实现者则可以在开放 ISA 的基础上探索新的微架构与专用扩展。S13

这里也有一个微妙的选择：如果目标是摆脱架构锁定，“全世界统一改用 Arm”并不等于最自由的结局。Arm 的架构与核心 IP 有商业授权模式，RISC-V 的基础 ISA 与标准扩展则是开放、免版税规范。开放 ISA 不等于免费获得先进 CPU 核心、EDA、验证 IP 或量产能力，但它把指令集本身从专有授权中独立了出来。S13 S17

RISC-V 眼下也没有成熟到能直接接管全球的高端 PC。2026 年一项面向实际硬件与软件栈的研究指出，现有实现的性能与系统集成水平仍然参差，尤其在通用高性能领域还需要继续追赶。S21 我愿意看到更多 RISC-V 方案进场，但不会把一张开放 ISA 规范误当成已经完工的桌面平台。

问题在于，全球迁移远远不只是给 GCC 或 Clang 换一个编译参数。

Windows on Arm 已经能通过 Prism 翻译运行不少 x86/x64 用户态程序，但微软明确说明：内核驱动不能靠这种翻译运行，必须提供原生 Arm64 版本。 游戏里的反作弊、专业设备驱动、闭源插件、企业虚拟机镜像、特定 ISA 的手写汇编和性能库，都可能成为真正的障碍。S14

普通人和工程师，到底用到了多少兼容性？

先问清楚在数什么。一个人在浏览器里看视频，应用本身用不到 16 位实模式；在现有 Intel 64 机器上，这个人按下电源键时，平台却已经走过旧启动路径。同一项机制，对应用是零次直接使用，对整台机器却是一次必经之路。把前一个数字当作“这项功能可以删除”的证据，就漏掉了固件。S05

换一个能自己核对的分母：列出我非做不可的任务，逐项问，如果改用 Windows on Arm，按我现有的软件和设备，哪一项还依赖 x86 二进制？ 这里数的是迁移依赖。它和“用过百分之多少条 x86 指令”是两个问题。

按图中的假设，日常组有 0/3（0%） 项任务依赖 x86 二进制。工程组有 2/3（约 67%）：用户态工具可以尝试翻译，仪器驱动却必须另找 Arm64 版本。如果测量必须用这台仪器，哪怕其他工作全能迁走，少这一个驱动也交不了实验报告。S14

这些比例只回答图中六项任务。把网页换成依赖旧插件的业务，把仪器换成已有 Arm64 驱动的型号，答案就会变。要回答某个实验室的真实比例，应该盘点它实际用的工具、插件、驱动和仪器，逐项验证；要估算可删的 CPU 逻辑，还得另查启动路径、虚拟化和异常行为。没人打开某个旧应用，并不会自动缩小芯片的验证范围。

Apple 给出了一条现实路线。它在 2020 年开启 Mac 向 Apple Silicon 的转换，用 Rosetta 为 x86-64 应用提供过渡。到 2026 年 9 月，Apple 已明确宣布 macOS 27 是通用 Rosetta 支持的最后一个大版本；未来只为某些依赖 Intel 框架的老游戏保留有限支持。S11 S12

这说明迁移可以做成，也说明迁移需要持续多年。Apple 能控制硬件、操作系统和软件分发；企业机房、DIY PC、科研设备、工业控制器与游戏生态则远比一条产品线分散。全球协同可以减少重复适配，却不能消灭每一个闭源程序和外设驱动的重写成本。

所以我想象的转型并不是“明天全网停机，后天统一换 ARM”。更合理的路线是：软件在 x86-64、AArch64 和 RISC-V 上都能构建与自动测试，主流组件维护跨架构基线；新项目尽量避免绑定某一家的 SIMD intrinsic 或二进制插件；硬件厂商则提供长期、可验证的驱动与系统接口。闭源遗留负载继续放在翻译器或老平台上，直到它们有足够的理由迁移。

这条路不必从说服 Intel 和 AMD 开始。先让软件不再把 x86 当成唯一默认平台，芯片厂商才有足够多的客户愿意试新架构。

我想让今天的设计者还能选

承认 x86 的成功很容易。今天最强的 x86 处理器里面，有大量值得学习的微架构设计；它们能把如此复杂的外部指令集执行得这么快，本身就是工程能力的证明。

可工程能力越强，我越觉得可惜。如此多优秀的设计人员，需要反复确认那些古老而微妙的架构行为仍然正确；同样的创造力，本来也可以用来探索更干净的软硬件接口。

有人会说，能跑旧程序就是实打实的价值。没错。兼容性曾让个人计算机产业快速扩张，如今又让许多公司不必为重写系统付账。只是这笔账没有消失，它被摊到了之后一代又一代的芯片和开发工具里。谁先放弃兼容，谁就要替整个软件世界垫付迁移成本；谁继续兼容，谁就能留住客户。这种局面靠任何一家公司的勇气都很难打破。

我希望有一天，开发者买一颗新的高性能 CPU，不必先关心它如何假装理解 1978 年的世界。Intel 和 AMD 也可以在更干净的架构上竞争缓存、分支预测、执行宽度和计算单元，Arm 和 RISC-V 则继续把新的设计者带进来。

到那时，我大概就不会再说 x86 是一坨狗屎了。它会变成一段很精彩、也终于可以放进博物馆的计算机历史。
